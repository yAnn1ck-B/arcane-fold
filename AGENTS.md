# Repository instructions

Eternal League is a local Tauri 2 / React / SQLite companion to MTG Forge. Read [DEVELOPMENT_PLAN.md](DEVELOPMENT_PLAN.md) for product scope and [docs/phase-5-release.md](docs/phase-5-release.md) before release work. Keep league rules built in and read-only, preserve earned progress, and avoid adding maintenance controls or manual ownership editing.

## Profiles and data preservation

- Production has the permanent identifier `com.eternalleague.desktop`. Never change it between production versions.
- `com.eternalleague.app` is the preserved legacy DEVELOPMENT profile. `npm run tauri dev` injects `src-tauri/tauri.dev.conf.json` unless an explicit `--config` / `-c` is supplied. Do not bypass this wrapper to start an ordinary debug app against the production identifier.
- `com.eternalleague.preview` is an isolated development preview that the user is actively playing. Preserve its current window, earned progress, database, and separate Forge exports unless the task explicitly requires otherwise. Earlier 184-card/64-wildcard/24-pack counts are historical controlled QA checkpoints, not current-state assertions or restoration targets. Never reset legitimate play to an old test baseline. Release artifacts must not include preview configuration, identifiers, databases, or debugging capabilities.
- Run native tests first, then rebuild and launch previews through `npm run tauri -- dev --config <explicit-preview-config>`. Cargo integration tests also rebuild the ordinary binary and can replace `target/debug/eternal-league.exe` with the default production context. Do not reuse a preview executable from before those tests; its identifier is embedded at compile time and cannot be changed by launch-time environment variables. Use a separate preview target directory when needed, and check the effective identifier and `database_info` before QA actions. An incorrect local launch was stopped with no production collection, decks, openings, operations, or league state; do not reset that profile as cleanup.
- Clean first production launch is achieved with the new production profile, not by deleting development files. Never copy legacy development/preview progress into production automatically. Existing Forge files are not an import source for league ownership.
- Never wipe an existing production database, reset progress on version change, clear artwork caches during updates, or delete unrelated Forge files. Use additive, tested migrations. Updates and reinstalls must preserve data; Windows uninstall preserves user data by default.
- After publication, never edit an existing SQL migration's bytes, including whitespace or line endings. Add a new migration instead.
- SQLx hashes exact migration bytes. Keep every SQL migration LF-only under `.gitattributes`; version validation and the native build guard reject CR/CRLF before embedding. Do not rewrite an applied migration or weaken runtime checksum validation. Add a new migration for schema changes. The backed-up, known-newline-only migration-7 correction in development/QA profiles is a one-time test-data repair, not a production migration or permission to rewrite arbitrary migration metadata.
- The real shared start is fixed at `1794847589` in `release-policy.json` and `src-tauri/league-rules.json`; validation must keep both identical. Keep it identical on all platforms and stable after first publication. Never derive it per install, build, platform, or later release. Legitimate late-join rewards are expected even for an otherwise clean production profile.
- `ETERNAL_LEAGUE_PREVIEW_WEEKS` is debug-only; release builds ignore it. Do not change the operating-system clock for tests. Do not apply preview rewards to the original development profile.

## Every publish requires a new version

The user intends to release through Codex. Every new publish must use a new, higher SemVer version. Never reuse a published version, move/delete an existing release tag, or replace published assets to conceal a change. Changes that alter the application, embedded configuration, or installer bytes after tagging require a new version and tag. Documentation-only and release-verification-tool-only fixes may be committed on main and used to verify an unchanged tagged candidate; they must not move its tag, rebuild/replace its artifacts, or reuse a published version. Every published release version remains unique and new. An unchanged failed workflow can be rerun without moving its tag.

Use the repository helpers:

1. Inspect the current version and release state. Run `npm run version:check`.
2. Run `npm run release:prepare -- patch`, `minor`, `major`, or an explicit higher `X.Y.Z`. Update the corresponding notes in `CHANGELOG.md`.
3. Confirm matching application versions in all five files: `package.json`, both root version fields in `package-lock.json`, the package in `src-tauri/Cargo.toml`, the `eternal-league` package in `src-tauri/Cargo.lock`, and `src-tauri/tauri.conf.json`. Config overrides must not introduce a different version. The tag is `vX.Y.Z`; updater metadata uses the same application version.
4. Complete required checks, commit the reviewed release candidate, and run `npm run version:check -- --tag vX.Y.Z`.
5. Run `npm run release:tag` from the clean release branch. It validates and pushes the current main branch with a new annotated immutable tag. The workflow creates a **draft** release.
6. Automatic Actions signing is currently enabled. In that mode, wait for both signed platform assets and matching updater metadata, then continue with full verification at step 10. Steps 6-9 below describe the local fallback. When using `RELEASE_SIGNING_MODE=local`, wait for the draft's two raw installers and run `node scripts/github.mjs exec node scripts/verify-release.mjs --tag vX.Y.Z --unsigned`.
7. Download the two raw draft assets with `node scripts/github.mjs release download vX.Y.Z --repo OWNER/REPO --dir .verification/releases/vX.Y.Z`, using the repository from `release-policy.json`.
8. Run `npm run release:sign -- vX.Y.Z [dir]` **directly**, not through the GitHub credential helper. The default directory is `.verification/releases/vX.Y.Z`. This LOCAL-only step uses `updater.key` and its DPAPI-protected password, strips GitHub tokens from the signer subprocess, binds signatures with Tauri's `--app-version`, and writes the two `.sig` files plus `latest.json`. It never uploads or publishes anything; private signing material stays on this PC.
9. Run `npm run release:attach -- vX.Y.Z [dir]` separately. It validates the draft, version, URLs, and signature contents, then uploads only the public signatures and updater manifest. Manifest URLs must use the final version tag and exact GitHub asset name, including any GitHub filename normalization; never use a draft's temporary `untagged-*` browser URL. A draft missing from the by-tag API is found through the authenticated release list.
10. Run `node scripts/github.mjs exec node scripts/verify-release.mjs --tag vX.Y.Z`. Require exactly five assets and actual minisign verification of both installers. Use `MINISIGN_EXECUTABLE` for a portable verifier if needed. Version-bound signatures are mandatory (`requireSignedVersion: true`). After attaching both signatures and the manifest, optional independent remote verification is `node scripts/github.mjs workflow run verify-release.yml --ref main -f tag=vX.Y.Z`; wait for that run to pass. It uses current main tools, requires the tag to match that main version, and verifies the unchanged draft with a checksum-pinned public minisign binary. Its `contents: write` permission exists only because GitHub requires push access to expose drafts; it does not upload, sign, or publish and uses no private signing secrets.
11. Publish only when the release request authorizes it and the concrete candidate is ready. Use an explicit, reviewed GitHub release metadata PATCH via `node scripts/github.mjs api repos/OWNER/REPO/releases/RELEASE_ID --method PATCH --input <reviewed-json-file>`. Include the exact `tag_name`, full `target_commitish`, `name`, `body`, `draft: false`, `prerelease: false`, and `make_latest: "true"`; re-read and verify the result. Then rerun verification with `--published` to check anonymous public downloads.

When editing draft notes/metadata before publication, send all those identity/state fields explicitly with `draft: true` and `prerelease: false`; do not rely on a partial body-only PATCH or CLI defaults. Re-read the exact release ID, tag, target commit, draft state, and asset list before and after. An accidental state/tag change must stop the release flow; never repair it by moving an immutable tag or replacing signed assets.

The unpublished `0.2.0` candidate was rejected after cross-platform SQL migration byte differences were found. Keep its tag immutable and never publish that candidate. The first public release was `0.2.1`. Current public release `0.3.0` was published unchanged on 2026-11-17 from immutable commit `1b22f49f534f1047d9b0026a5d16b2d39fd60b9d`; always inspect current versions and release history, and use a higher version for the next publish. The initial-release policy and shared league anchor remain historical/stable values, not the latest release version.

## Signing and credentials

- Keep updater private keys, key passwords, GitHub credentials, and tokens secret. Never commit, print, paste into docs, or persist them in release artifacts or command logs. A public updater verification key may be committed.
- Use `scripts/github.mjs` for authenticated local GitHub operations. It obtains the credential in memory and supplies `GH_TOKEN` only to its child process. Do not replace this with commands that echo credentials, dump the environment, or write tokens to files.
- Version 0.2.1 used LOCAL signing: CI built raw installers, Codex signed them offline, and a separate attach step uploaded only public signatures and updater metadata. This remains a fallback. Future Actions signing is explicitly authorized using the same established signing identity and repository Secrets. Do not regenerate or rotate the key casually.
- Automatic approval review initially rejected credential export and public release actions while explicit consent was missing. The user subsequently explicitly approved all three: storing the encrypted updater key and password as GitHub Actions secrets, making the repository public with source/history visible, and publishing the unchanged verified v0.2.1 assets. This consent supersedes those earlier pending blocks; it does not authorize printing/committing secrets or exposing unrelated credentials.
- The established `TAURI_SIGNING_PRIVATE_KEY` and `TAURI_SIGNING_PRIVATE_KEY_PASSWORD` repository Secrets are configured; names and timestamps were verified without reading/logging their values. The user separately explicitly approved **Enable automatic CI signing**, and repository variable `RELEASE_SIGNING_MODE=actions` is now active and verified. Real Secrets signing-check run 43987014045 passed: a harmless fixture was signed in Actions and verified against the committed public key and expected signed version without private output. Verify secret names and workflow success without retrieving or logging values. In Actions mode, wait for both signed platform assets, matching latest.json, and full cryptographic draft verification; do not run local attachment steps unnecessarily. Every future publish still requires a new higher synchronized version and immutable tag. Local signing remains available if Actions mode is disabled. The first complete application release using Actions signing is now verified: [v0.3.0 workflow 44055179189](https://github.com/yAnn1ck-B/eternal-league/actions/runs/44055179189) passed both platforms and full signed-draft verification. Publication and anonymous installer/updater verification also passed. Keep the earlier fixture signing check as historical evidence.

## Required release verification

- Use the lockfiles (`npm ci`), pass the production frontend build, native tests, and version validation, and inspect the tag workflow result.
- Verify Windows NSIS `.exe` and Linux `.AppImage` outputs, their updater artifacts/signatures, and matching `latest.json` versions, platforms, and download URLs. A successful frontend build alone is not a completed release.
- Validate a clean production first launch: correct production identifier; no inherited collection, decks, history, receipts, or development queue; legitimate shared-calendar rewards only; detected Forge paths; catalog setup; working artwork.
- Test installation, uninstall/reinstall, and signed upgrade preservation using isolated fixtures on both supported platforms. Keep evidence and any genuine limitations in the release verification notes; never claim an unperformed check.
- **Unreleased policy, explicitly requested after 0.3.0:** production requires successful online version verification before normal use. Only updater state `current` unlocks the league; startup, focus, reconnect, and five-minute rechecks may block it again. Remove Later/dismiss escapes. Offline/check failures and known-update download/signature/install/restart failures remain blocked with retry actions; retain explicit download/install/restart steps and signature verification. Development/preview builds bypass this production gate.
- While blocked, allow only the repair needed to finish already-pending deck saves, limited to the current deck and Forge folders; keep other league use and mutations blocked. Preserve progress and never add reset-on-update behavior.
- Published 0.3.0 retains its optional updater. It needs one ordinary upgrade to adopt the new policy; do not claim that already-shipped clients can be retroactively forced. Client startup/focus/reconnect/periodic checks do not guarantee simultaneous central-server lockstep across all devices. No version bump, tag, or publication is implied by this policy change.
- Keep `README.md`, the development plan, changelog, and release verification notes aligned with the actual shipped behavior. Preserve older test records as historical rather than rewriting them as current evidence.
